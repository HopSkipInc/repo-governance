## TL;DR

What PDD Kit does:
- An agent asks clarifying "decision cards" before writing anything.
- It records the answers in an intent artifact.
- It turns the parts it can formalise into Verus specs on Rust code.
- It proves the code meets them for every input.
- It writes a planned test for every assumption the proof cannot check.
- The PR becomes a receipt: each requirement is marked *proved* or *checked by test*.

**The prover is not ours to ship:**
- The templates are "not specific to any language" (README).
- No governed client is Rust.
- PDR-007 keeps this practice out of assurance positioning.

**Verdict: STEAL IDEAS, methodology only.** Most of the governance shape around the prover is
already here, in local vocabularies. The steal is:
- one evidence vocabulary
- a stop rule that also covers weakening the *spec*
- a sharper question bank for #119

## Gap analysis (top 5)

**1. Seven evidence vocabularies, and no receipt for each requirement**
> **Their approach:** every requirement on the PR is labelled proved or empirically checked. A plan entry reads *planned* until it runs, then records the command and the commit.
>
> **Our current state:** each vocabulary above is correct where it lives. None is attached to a Verifiable outcome when the PR opens, so a reviewer has to rebuild "which outcome rests on what" by hand.
>
> **Relevance:** HIGH. This is the thing PDD makes reviewable without reading code, and it needs no prover.
>
> **Existing issue:** none. #60–#63 (brief join key) are adjacent. ai-fleet #4089 would consume this.
>
> **Candidate action:** file a new issue. Each Verifiable outcome gets one evidence kind in the PR body:
> - `exhaustive`: the whole finite domain was checked.
> - `sampled`: example or integration tests.
> - `live`: a control run against a deployed revision.
> - `judged`: human or LLM review.
> - `not-run`: never a pass.
>
> The kinds must be readable in the founder register (PDR-003). A repo with a prover may add `proved`.

**2. The stop rule covers tests, not the spec, and the template contradicts itself**
> **Their approach:** "stops to ask rather than weaken a contract". The contract is the spec, not the test.
>
> **Our current state:**
> - The stop condition names "weakening a test, assertion, or matcher". Editing a Verifiable outcome or a proof-of-failure rule to fit what was built is not named.
> - `templates/agent-routing.md`'s canonical "Observable stop conditions" list (:408-423) omits both v1.12.0 conditions. The AGENTS.md section it ships (:820-832) carries both, so a client reading the policy body sees an older list.
>
> **Relevance:** HIGH. Rewriting the spec to fit the build is the weakening that leaves no negative diff for `check-weakened-verification.mjs` to catch.
>
> **Existing issue:** none.
>
> **Candidate action:** file new issues, split two ways:
> - Reconcile the list. This is mechanical, standard tier.
> - Decide whether spec-weakening becomes a stop condition. This needs a decision. Its mechanical half could be an outcome-set snapshot taken at pickup and compared at PR time.

**3. "Gate-backed" means the gate's file exists, not that it rejects a violation**
> **Their approach:** plant one bug per spec clause. The verifier must reject each one on the clause it targets, or that clause constrains nothing.
>
> **Our current state:** `check-claim-coverage.mjs` counts a gate as backing when the path it names exists. The doc states the limit itself: it checks that a gate exists, not that it is wired (`docs/claim-backing-example.md`). The fixture floor only proves rejection for this repo's own scripts.
>
> **Relevance:** MEDIUM. Today it scores an existing gate as backing even if the gate never fires.
>
> **Existing issue:** none. PDR-008 forecloses a second enumerator and templating it before a client has run the contract.
>
> **Candidate action:** watch. Later, add a **demonstrated** grade to the one enumerator: the gate's fixture names the claim and fires on a planted violation of it.

**4. Decision cards: #119 can take three specifics**
> **Their approach:**
> - The first card catches that "only with the right password" is met by refusing everyone, so the spec needs the converse too.
> - Each card explains the code before it asks.
> - Each card names what every option costs, e.g. "proving more of login means trusting more small wrappers".
> - In Chopin, answers are stored apart from the prose so "a later rewrite cannot silently change what the team decided".
>
> **Our current state:** #119 is ready but unbuilt. backlog-groom already refuses to edit bodies, because that is "how intent gets laundered".
>
> **Relevance:** MEDIUM. Cheap additions to a procedure that is already specified.
>
> **Existing issue:** #119. ai-fleet #3761 installs it.
>
> **Candidate action:** comment on #119 with three additions:
> - For every refusal outcome, ask for the matching admission outcome.
> - Cards explain the code and price each option.
> - Answers are recorded apart from the body prose and attributed to whoever gave them.

**5. Assurance belongs in coverage, not in routing**
> **Their approach:** the proved core and the trusted ring are separate claims. The guarantee is "only as strong as the six trusted pieces".
>
> **Our current state:** #135 proposes `risk:` facts only. Proof or exhaustive checking is a *mitigating* fact.
>
> **Relevance:** MEDIUM. Without a written rule, a proved surface invites a tier downgrade.
>
> **Existing issue:** #135.
>
> **Candidate action:** comment on #135.
> - A proved or exhaustively checked surface is a testing-strategy coverage status.
> - It retires `risk:uncovered` for the covered clauses only.
> - The trusted boundary stays uncovered until its tests exist.
> - It is never a downgrade on its own (agent-routing: "you may never downgrade").

## What we do not take

- **Verus, or any prover, as a template.**
  - README: "Specific to any language or stack" is listed under *What this is not*.
  - No client in `downstream/hopskip/_client.md` is Rust.
  - PDR-006 says no infrastructure before the practice needs it.
  - PDR-007 says this is not a security or compliance practice.
  - If a Rust client arrives, it is a conditional `/analyze-repo` row under PDR-009, not a class.
- **An LLM gap reviewer as a gate.** The DoD says "only deterministic checks belong in gates", and PDD agrees: Verus gates, while the LLM reviewer loops back.
  - Latent conflict: merge-path D1 says a reviewing agent's analysis "reported as a check, is a gate".
  - Resolve that before anyone proposes an LLM verifier as a check.
- **Test pruning.** Proven behaviour lets them prune tests. Without a proof tier, there is nothing here that licenses deleting a test.

---

## Decision

**STEAL IDEAS (methodology only).**
- The prover is language-specific, and the templates are not.
- Everything around the prover maps onto templates we already ship: decision cards, a receipt per requirement, stop rather than weaken the contract, and the trusted-boundary list.
- The work is to unify and tighten them, not to add a layer.

**New PDR needed?** No.
- These are template changes under PDR-001/003/006/007.
- None of them moves a product bet.

## Notes / Quotes worth keeping

- PDD: "pdd-prove plants one bug per ensures clause … and Verus has to reject each mutant on the clause it targets."
  - Our version, `templates/issue-authoring.md`: a proof-of-failure criterion "is satisfied by the easiest available failure, not the one you meant."
  - Both reach the same rule from opposite ends.
- PDD: "A passing test only shows the code worked on the inputs it tried, so PDD Kit labels it as evidence rather than proof."
- PDD: "When a model writes its own spec … it tends to land on weak invariants: clauses that verify but rule out almost nothing. … We call that 'vibe verification.'"
  - Our version, design-lenses §5.2: a lint that passes on "it's fine" "converts a judgment into a green check".
- PDD FAQ: "Models write the spec, code, and proof, but only a deterministic Verus run decides whether it passed."
