# Governance update: generated system maps (2026-08-07)

**Applies to:** all governed repos, both `full` and `core` adoption class. For `core`
repos this is one workflow, one committed directory, and one README line — there is no
lighter version to negotiate.
**Policy version to install:** whatever `templates/system-map.md` currently stamps — read
it, do not assume. This prompt deliberately does not name a version.
**Templates:** `templates/system-map.md`, `templates/workflows/graphify-report.yml`
**Status of this policy:** candidate, designed in one session and not yet run anywhere.
Report friction rather than working around it.
**GETTING_STARTED:** deliberately not in step 1 for new adoptions — this install wave is
the proving ground. Revisit once it has run clean across the estate for a few cycles.

## Why

Every new team member has the same moment: their beautiful new code in one repo breaks
something in the real world because they didn't understand the graph — which services
exist, what talks to what, what breaks if they change this. Orientation knowledge is
currently tribal and walks around in people's heads.

This adds a generated system map to every repo: a committed knowledge graph
(`graphify-out/`) produced by CI, rendered for humans as `GRAPH_REPORT.md` (linked from
the README) and read by coding assistants directly from the clone. Per-repo graphs are
also the feed stock for a future estate-level map — adoption here is what makes the
estate merge cheap later.

The failure modes this prevents, in order of how much they hurt: onboarding by
interruption, agents grepping cold on every task, and (if we skip the pinning rule) an
unpinned third-party CI install replicated across the estate.

## Steps

**1. Install the policy and the workflow.**

```bash
cp ~/repos/HopSkipInc/repo-governance/templates/system-map.md docs/system-map.md
cp ~/repos/HopSkipInc/repo-governance/templates/workflows/graphify-report.yml .github/workflows/graphify-report.yml
```

Open the workflow and set `on.push.branches` to this repo's default branch (`main` vs
`master`). Nothing else needs local customization.

**2. Decide the commit-back path.** The workflow pushes a bot commit to the default
branch. If branch protection requires PRs here, either (a) allow the Actions bot to
bypass for this workflow, or (b) convert the commit step to an auto-PR. Record which
you picked in the PR that installs this — the audit sweep will ask.

**3. Add `.graphifyignore` if needed.** `.gitignore` is respected automatically. Add
`.graphifyignore` with defense-in-depth exclusions for anything credential-shaped
(`.env*`, `*.pem`, `*.key`) plus vendored/generated dirs not already ignored.
`graph.json` is committed to the repo — exclusions are cheaper than explanations.

**4. Add the README line.** One line, written by you, in whatever section fits:

```markdown
- **System map** (auto-generated by CI): [graphify-out/GRAPH_REPORT.md](graphify-out/GRAPH_REPORT.md)
```

This is the only README change this policy will ever make. The workflow never touches
human prose; you never touch `graphify-out/`.

**5. Run it once manually.** `gh workflow run graphify-report.yml`, then confirm the
bot commit lands (`chore: refresh system map [skip ci]`) and `GRAPH_REPORT.md` renders.
First run is a full extraction — subsequent runs are incremental.

**6. Record the install.** Append to the Applied-governance list in CLAUDE.md (repos
that carry the governance-sync section) or note it in the PR body otherwise:
`[2026-08-07-graphify-system-maps.md] — applied <date>`.

## Explicitly out of scope

- **Semantic (LLM) extraction of docs/PDFs.** Code-only is the installed default. If a
  repo wants doc-level semantics, that is a separate opt-in with its own prompt — do
  not add API keys to this workflow.
- **Web-publishing the map.** `graph.html` is local-open only. Never deploy graph
  artifacts to anonymous static hosting (see `docs/system-map.md` §Publishing rules).
- **Cross-repo runtime edges.** Proving which service actually points at which
  database/endpoint from Azure runtime config is infra-ops' collector work, governed by
  its own downstream prompt. Repos do not inspect other repos' runtime config.
